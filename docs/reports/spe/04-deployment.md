# Deployment

The Deployment process brings up all the microservices, together with their own databases and the Kafka
broker, as a single running system. _Munchies_ supports two local deployment targets: Docker Compose, used for quick,
disposable runs of the system and for our end-to-end tests, and Kubernetes, used to run the system on a
production-like, orchestrated cluster.

## Docker Compose

We use Docker Compose as a lightweight alternative to a full orchestrator: it lets us bring up the whole system, or
part of it, on a single machine without the overhead of a Kubernetes cluster. We rely on it in two situations: to
manually try out the whole system end-to-end on our own machines, and to automatically provide the running
environment for our end-to-end test suite.

### Compose files

The configuration lives under [```config/```](https://github.com/Norby99/munchies/tree/master/config), split into
three files, one per concern:

- [
  ```config/kafka/docker-compose.yml```](https://github.com/Norby99/munchies/blob/master/config/kafka/docker-compose.yml):
  a single-node Kafka broker, shared by every service that communicates asynchronously.
- [
  ```config/mongodb/docker-compose.yml```](https://github.com/Norby99/munchies/blob/master/config/mongodb/docker-compose.yml):
  one MongoDB instance per service, each with its own named volume and exposed port, reflecting our
  "database per service" rule.
- [
  ```config/service/docker-compose.yml```](https://github.com/Norby99/munchies/blob/master/config/service/docker-compose.yml):
  the microservices themselves, built from the Dockerfiles generated by our Gradle build, each wired to its own
  database and to Kafka.

Keeping them separate lets us, for example, start only the infrastructure (Kafka and Mongo) and run a single
service from the IDE against it, which is convenient while debugging.

Every container exposing an HTTP API declares a healthcheck against its own health endpoint, and every
```depends_on``` waits on that healthy state rather than just on the container having started, so that a service is
never started before its database, nor before any other service it calls directly:

```yaml
order-service:
  depends_on:
    munchies-mongo-order-service:
      condition: service_healthy
  healthcheck:
    test: [ "CMD", "curl", "--fail", "--silent", "http://localhost:8080/health" ]
```

### Gradle integration

Instead of calling ```docker compose``` directly, we wrapped it in a Gradle convention plugin, built on top of the
[```gradle-docker-compose-plugin```](https://github.com/avast/gradle-docker-compose-plugin), so that the three files
above stay in sync with the rest of the build. Running ```./gradlew composeUp``` rebuilds every service's Docker
image from its current sources, then starts the whole stack and waits for every exposed port to become reachable;
```composeDown``` tears it back down, and ```composeShowDb -Pservice=<name>``` runs a one-off query against a given
service's database to inspect its collections, which is handy for manual checks.

```./gradlew composeUp``` is the command we reach for ourselves whenever we want to try something against the real
system instead of mocks. It is also how our end-to-end test suite gets its environment: the ```e2eTest``` task
depends on ```composeUp``` and is ```finalizedBy composeDown```, so ```./gradlew e2eTest``` builds, starts, tests
against and tears down the whole stack with no manual step in between. This is the same mechanism used by the
`test` CI workflow described in [CI/CD Workflows](03-devops/cicd.md).
